Viabilidad de SDD en Entorno Corporativo

Evaluación del Desarrollo Guiado por Especificaciones (Spec-Driven Development) como modelo de gobernanza, calidad contractual y aceptación técnica para entregas de proveedores.

1. Resumen ejecutivo

Este informe evalúa la viabilidad del SDD para que el Product Owner (PO) gobierne nuevos desarrollos y mantenimientos evolutivos realizados por proveedores externos, garantizando trazabilidad y cumplimiento en entornos con alta exigencia de fiabilidad y seguridad.

Modelo: Spec-anchored

La especificación vive en el repositorio junto al código. En cada evolutivo se tramita un delta; tras la aceptación, el delta se fusiona en la especificación vigente.

Frontera contractual clara

Separación estricta entre el contrato funcional del PO (requisitos, escenarios y matriz de aceptación) y la solución técnica del proveedor (diseño y tareas).

Exigencia por artefactos

Al proveedor no se le impone una herramienta ni IDE concreto, sino la entrega de artefactos estandarizados: spec técnica, tests automatizados y matriz ejecutada.

Reutilización de activos

Conexión directa con la base documental de ingeniería inversa y el RAG corporativo para generar specs base en aplicaciones existentes sin rehacer inventarios.

2. Fundamentos y alcance del SDD

Qué es: El SDD convierte una especificación estructurada en la única fuente de verdad: el código, las pruebas automatizadas y los criterios de aceptación se derivan de ella y se verifican contra ella.

  • Markdown estructurado: Requisitos formales (patrones EARS) y escenarios de aceptación DADO/CUANDO/ENTONCES (Gherkin).
  • Contratos de interfaz (YAML/JSON): Esquemas OpenAPI o JSON Schema procesables por herramientas de automatización.

4. Flujo operativo y gobernanza contractual

  
El ciclo de vida del SDD institucionaliza la revisión previa y blinda la aceptación final frente a interpretaciones ambiguas:


  

  

  


  
Cláusulas contractuales mandatorias

  
    
    
  • Artefactos obligatorios: La entrega formal exige código fuente, batería de pruebas automatizadas enlazadas, informe de CI y matriz acceptance.md completa.
    • 
    
  • Criterio de entrada estricto: Si al entregar falla una sola prueba del proveedor, la entrega no se admite administrativamente y los plazos contractuales siguen corriendo.
    • 
    
  • Aceptación vinculante: La aceptación del PO se ejecuta exclusivamente sobre los escenarios acordados en la versión congelada. Cualquier petición adicional constituye un nuevo evolutivo.
    • 
    
  • Rondas de subsanación acotadas: Máximo de dos rondas de corrección de defectos encontrados en preproducción antes de aplicar penalizaciones.
    •

Reglas de coexistencia

    
    
      
  1. Prevalencia: En caso de discrepancia entre el RAG y la spec versionada, manda siempre la spec vigente. El RAG aporta contexto, pero no tiene validez contractual.
    2. 
      
  2. Consumo desacoplado: El contrato jamás enlaza respuestas directas del RAG. El PO reescribe la información como requisitos formales con identificador.
    3. 
      
  3. Ciclo de vida de la ingeniería inversa: Las afirmaciones extraídas de código se etiquetan como [INFERIDO] hasta que un evolutivo las valida mediante pruebas, pasando a [CONFIRMADO].
    4. 
      
  4. Exposición segura: Se recomienda exponer el RAG y las bases técnicas al PO mediante servidores MCP (Model Context Protocol) de solo lectura. Para los proveedores externos se entrega un paquete de contexto acotado al cambio.

8. Riesgos, buenas prácticas y hoja de ruta

  
  

    

      
Riesgos identificados

      
    
        
  • Teatro de especificación: Redactar documentos exhaustivos que no se utilicen para la aceptación real.
    • 
        
  • Deriva spec-código: Cambios aprobados en código sin actualizar la spec vigente.
    • 
        
  • Verbosismo IA: Textos generados extensos pero carentes de precisión contractual.
    • 
      

    

    

      
Buenas prácticas

      
    
        
  • Deltas atómicos: Especificaciones de 5 a 15 requisitos entregables de forma independiente.
    • 
        
  • Trazabilidad estricta: Todo escenario debe tener un identificador que coincida con el test de CI.
    • 
        
  • Revisión humana obligatoria: Ninguna spec pasa a desarrollo sin firma formal del PO.
